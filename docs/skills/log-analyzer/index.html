🔎 交互式日志源与编码排查器

切换 4 类常见排障现场，查看 log-analyzer 的采样策略、生产连接授权门禁与 Windows 编码防坑动作：

📂 本地只读 · 禁止整文件直接载入 适用：Nginx / Spring Boot / JSONL / syslog

先查体积、行数与首尾各 20 行样例，再按时间窗分块流式过滤

面对几十 MB 甚至 GB 级应用日志，绝不一次性塞进上下文。先识别结构化（JSON Lines / Logfmt）或文本日志格式、统一标注时区（如 UTC+8 / UTC），再按级别与关键字定向采样。

采样与聚类动作 按时间窗、FATAL/ERROR/WARN 或 tail 流式筛选，剥离 UUID、时间戳与 requestId 做相似异常去重聚类。
因果链与指标核查 按时间戳与 traceId 区分源头异常（如连接池超时）与级联次生报错；仅在日志含真实字段时统计 4xx/5xx 与 P50/P95/P99。
脱敏与只读边界 输出自动遮蔽密码、Token、Cookie、手机号、身份证与内网密钥；绝不清理、截断或轮转原日志文件。
排查提示：检查文件体积与编码 → 锁定故障时间窗（明确 UTC+8 或 UTC）→ 抽取 Top 异常模式与代表性行号（如 app.log:18420）。

🧭 4 步结构化日志取证流程

1

检查来源、体积与文件编码

确认来源为本地文件、粘贴片段或经授权的只读输出；先查大小、编码（UTF-8 / UTF-16LE / GBK）与首尾各 20 行样例，识别 JSON Lines、Logfmt、Nginx、Spring Boot、FastAPI、Go/Node 或系统日志格式。

2

定向过滤、统一时区与去重聚类

明确故障时间窗与时区（防止跨服务 UTC 与 UTC+8 错位误判因果），按 FATAL/ERROR/WARN、服务名或 traceId 过滤，并剥离变动参数对重复报错做模式聚类。

3

异常峰值与因果链追溯

统计 Top 异常次数、首次出现、峰值与恢复时间，通过时间戳和 traceId 区分“源头异常”与“级联次生报错”；仅在日志确实包含耗时或状态码字段时汇总 P50/P95/P99 与 4xx/5xx 分布。

4

输出脱敏中文报告与证据等级

输出含来源编码、Top 异常聚类表、根因证据等级（已实证 / 待进一步验证）及排查建议的结构化报告，每条结论都带真实行号或 traceId 证据，绝不臆造指标。

🛡️ 生产连接门禁与工具分工

🚨 生产环境与隐私的四道红线
  • 大文件零整读：超过数 MB 的日志必须分块流式过滤，避免上下文溢出或内存暴涨。
  • 远程/生产连接前必须确认：连接生产 Docker、Kubernetes、SSH 主机或 AWS CloudWatch / 阿里云 SLS 前，先确认目标环境、查询时间窗与只读权限范围，严禁重启、清理或修改线上配置。
  • 严格脱敏：示例日志行与汇总表必须遮蔽密码、Authorization Header、Token、Cookie、手机号、身份证号和真实内网密钥。
  • 严禁破坏现场：只输出只读排查结论与改进建议，不擅自清理、截断或轮转线上日志文件。

❓ 常见问题 FAQ

几百 MB 的线上 .log 文件会不会把上下文直接撑爆？

不会。log-analyzer 禁止整文件直接载入，会先检测体积、行数与首尾样例，再通过时间窗、日志级别、关键字或尾部采样分块过滤。

为什么专门强调 Windows UTF-16LE 和 GBK 编码坑？

国内大量研发与运维在 Windows PowerShell 5.1 下习惯用 > 重定向保存日志，默认会生成带 BOM 的 UTF-16LE 文件；而中文 Windows 终端或老系统常输出 GBK / CP936。先识编码再读，才能避免乱码和 UnicodeDecodeError。

日志里如果没有耗时字段，报告会不会硬编 P95/P99？

绝不会。规则明确约定只有当日志里真实存在对应字段时才统计 HTTP 4xx/5xx 与耗时分位，否则只在「改进建议」中提示补充埋点字段，杜绝虚构指标。

贴一段包含 Bearer Token 或用户手机号的日志安全吗？

技能要求所有输出报告中的示例日志行与聚类摘要自动脱敏密码、Authorization Header、Token、Cookie、手机号与身份证号；同时也建议你在上传生产日志前优先做好源头脱敏。
