🛡️ 交互式高危漏洞维度排查器

切换 4 类高频安全维度，查看 security-audit 如何基于真实数据流判定可达性置信度、守住只读边界并输出脱敏修复建议：

🔴 高危 · 优先核实数据流 置信度规则：区分已确认与疑似 只读边界：绝不发送注入载荷

SQL / NoSQL / 命令注入与路径遍历核验

数据流核验链：外部输入（req.query / body / 文件名） → 是否经过参数化或白名单规范化 → SQL 拼接 / shell=true / 任意路径读写

🎯 可达性置信度判定

  • 已确认（高置信）：不可信输入未经参数化直接拼入 SQL 或传入 shell=true 命令执行点
  • 疑似（待复核）：存在拼接写法，但上游参数来源或网关校验逻辑未纳入当前审计目录
  • 排除误报：已采用预编译占位符或严格白名单映射的语句，不虚报高危

🚧 只读边界与跨技能分工

  • 只读分析源码，绝不构造真实 SQL/Shell 攻击载荷打本地或线上接口
  • 不提供武器化利用脚本（exploit），仅给出最小可验证修复代码
  • 若疑点来自第三方 ORM 或驱动版本已知 CVE，移交 dep-auditor 查 lockfile
// 修复前（脱敏示意）：直接拼接用户输入 db.query("SELECT id, name FROM users WHERE email = '" + email + "'"); // 修复后：统一改用参数化查询 db.query("SELECT id, name FROM users WHERE email = ?", [email]);

🧭 触发边界与安全技能分工

避免一个 Skill 乱揽活导致“凭记忆编造 CVE”或“把代码风格当高危漏洞”，security-audit 与同仓其他技能职责切分明确：

✅ 交给 security-audit

  • 指定目录、业务模块、HTTP API / Webhook / 文件上传接口的源码级静态安全审计；
  • 排查硬编码密钥、SQL/命令注入、JWT/IDOR 越权、不安全反序列化、XSS/CSRF/SSRF 与敏感日志泄露；
  • 生成含 文件:行号、置信度评级、潜在影响和脱敏最小修复方案的中文报告。

🚫 不适用场景（交由对应技能处理）

  • package.json / lockfile / requirements.txt / go.mod / Cargo.lock 等第三方依赖 CVE 与许可证核验 → 请转 dep-auditor（本技能严禁凭版本号猜测 CVE）；
  • 梳理 .env* 变量清单与 .gitignore / 客户端前缀泄露 → 请转 env-manager；
  • 常规功能 Bug 与代码可读性审查 → 请转 zh-code-reviewer；
  • 针对线上或外部目标的主动渗透测试、端口扫描或漏洞利用 → 严禁执行。
⚠️ 凭据零回显与密钥轮换红线

当静态扫描检出硬编码 API Key、数据库密码或私钥时，报告中只输出脱敏后的 文件:行号 与变量名，绝不把真实凭据原文回显到报告或聊天窗口；同时明确提醒立即撤销并轮换凭据，而非仅删除代码行。

📋 三层威胁面排查清单与报告结构

🔴 高危（优先核实可达性）

  • 硬编码密钥 / API Key / 私钥 / 数据库密码
  • SQL / NoSQL / LDAP 注入与命令注入（shell: true / os.system）
  • 路径遍历与任意文件读写（未校验基目录前缀）
  • 不安全反序列化（pickle.loads、不安全 YAML load）
  • 认证授权缺失（JWT 签名/alg: none、IDOR 越权）与 SSRF

🟡 中危（重点防滥用）

  • XSS（未转义用户输入直出 DOM 原始 HTML / React 危险原始 HTML 注入属性 / 模板原样输出）
  • CSRF 防护缺失或 Cookie 漏配 HttpOnly / Secure / SameSite
  • 密码学缺陷（弱哈希存口令、可预测随机数作验证码/令牌）
  • 敏感信息写入日志、异常响应或前端 Bundle
  • 过宽 CORS（* 配 Credentials）或缺失限流

🟢 低危与加固建议

  • 缺少安全响应头（CSP、HSTS、X-Content-Type-Options）
  • 报错堆栈暴露内部物理路径或框架版本
  • 临时文件权限过宽或未强制 HTTPS
  • 显式列出「未覆盖范围」（如运行时网关配置、第三方依赖建议交 dep-auditor）

❓ 常见问题 FAQ

security-audit 和 dep-auditor 的职责分工是什么？

security-audit 专注业务源码与配置的静态安全审计（注入、越权、硬编码密钥、XSS、SSRF、反序列化等），严禁凭版本号猜测第三方包 CVE；package.json、lockfile、requirements.txt、go.mod、Cargo.lock 等第三方依赖漏洞与许可证事实核验应交给 dep-auditor。

执行 security-audit 时会自动修改业务代码或向服务发测试攻击包吗？

不会。security-audit 默认严格只读，只分析源码与配置，绝不擅自改写文件，也不向本地或线上服务发送攻击载荷、端口扫描或验证性越权请求；仅在用户明确要求修复并确认范围后才修改源码并复验测试。

如果扫描出代码里写死了 API Key 或数据库密码，报告会怎么处理？

报告严禁回显任何真实密钥、Token、密码或私钥明文，只记录脱敏后的「文件:行号」与变量名，并在修复优先级中提醒用户立即撤销并轮换已泄露的凭据，而不是仅删除代码行了事。

为什么报告要区分「已确认（高置信）」和「疑似（待复核）」？

静态正则搜索很容易把已参数化或由上游网关拦截的代码误报为高危漏洞。security-audit 要求沿着输入源（Source）到校验过滤再到危险汇聚点（Sink）追踪数据流：路径完整且无有效拦截才标「已确认」，上游中间件或运行时配置不在本次读取范围内时诚实标「疑似（待复核）」。
