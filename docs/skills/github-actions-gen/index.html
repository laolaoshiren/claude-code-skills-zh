🎛️ 交互式 CI/CD 模板选型器（安全基线预览）

按技术栈切换查看 github-actions-gen 盘点的真实项目证据、最小 permissions 策略、Action 40 位 SHA 固定规则与超时控制骨架：

Node.js / TypeScript 只读 CI 模板

证据源：package.json · .nvmrc · package-lock.json
1. 最小 permissions 边界

顶层锁定 contents: read；fork PR 不接触 Secrets 与写权限，checkout 默认 persist-credentials: false。

2. Action 固定与缓存策略

全部 Action 必须从官方 release 核验完整 40 位 SHA 并附版本注释；缓存 key 绑定真实 lockfile（npm / pnpm / yarn），绝不缓存凭据。

3. 超时与并发控制

每个 job 显式设置 timeout-minutes: 15 与 concurrency.cancel-in-progress: true，避免挂死任务耗尽配额。

.github/workflows/ci.yml（安全结构示例 · 生成时实时核验官方 40 位 SHA） 
name: CI
on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

permissions:
  contents: read

concurrency:
  group: ci-${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true

jobs:
  test:
    runs-on: ubuntu-latest
    timeout-minutes: 15
    steps:
      - uses: actions/checkout@<40位官方核验SHA> # vX.Y.Z
        with:
          persist-credentials: false
      - uses: actions/setup-node@<40位官方核验SHA> # vX.Y.Z
        with:
          node-version-file: .nvmrc
          cache: npm
          cache-dependency-path: package-lock.json
      - run: npm ci
      - run: npm run lint
      - run: npm test
      - run: npm run build

🧭 威胁模型优先的 7 步 CI/CD 生成流程

1

盘点真实项目证据

先读 package.json、.nvmrc、pyproject.toml、go.mod、Cargo.toml、Dockerfile 与既有 .github/workflows/，确认真实脚本、monorepo 边界与矩阵维度；脚本缺失先指出缺口，不靠猜测编命令。

2

建立触发器威胁模型

把 pull_request 视作不可信代码（只读 Token、零 Secrets、不跑高权限自托管 Runner）；绝不在 pull_request_target 中 checkout 或运行 PR 代码；所有 ${{ github.event.* }} 不可信输入必须经 env: 传递，防 shell 注入。

3

按职责拆分流水线

默认只落盘只读 ci.yml（lint / test / build）；仅在用户明确授权并确认环境、OIDC、required reviewers 与回滚方案后，再单独拆分 release.yml 或 deploy.yml，且只给发布 job 所需写权限。

4

核验官方 Release 并固定 40 位 SHA

从 Action 官方仓库解析完整 40 位 commit SHA，写成 uses: owner/action@<40位SHA> # vX.Y.Z；对 actions/checkout 默认设置 persist-credentials: false，并在交付说明里标注 SHA 来源与核验时间。

5

实测语法与本地命令验证

依次运行 actionlint（若未安装如实说明缺口）、YAML 解析检查、uses: 全量 SHA 扫描、本地 lint/test/build 复验及最终 git diff 审查，确认无 Token、真实 webhook 或 .env 泄露。

🛡️ 供应链安全红线与交付核对清单

每份生成 Workflow 的强制标配

  • 命令、运行时版本与 lockfile 均来自真实仓库文件，不凭项目名瞎猜；
  • 所有第三方 Action 固定 40 位完整 SHA 并附版本注释；
  • 顶层及各 job 均配置最小 permissions、timeout-minutes 与并发取消；
  • 发布部署优先采用短期 OIDC、受保护 GitHub Environment 与可验证回滚方案。

明确禁止的高危反模式

  • 禁止在 uses: 中使用 @main、@master、@latest 或可移动的 @vN tag；
  • 禁止在 pull_request_target 中 checkout PR head 或运行 PR 脚本/依赖；
  • 禁止把 ${{ github.event.pull_request.title }} 等表达式直接拼进 run: shell；
  • 禁止在未获要求时擅自新增 README-CICD.md 等冗余文档或把 Secrets 写入日志/缓存。

❓ 常见问题 FAQ

为什么所有第三方 Action 必须固定为完整 40 位 commit SHA，而不能写 @v4 或 @main？

分支引用与语义化 tag 都属于可变指针，上游一旦被劫持或误覆盖，仓库 CI 会静默执行恶意代码。使用 uses: owner/action@<40位SHA> # vX.Y.Z 后，SHA 锁定不可变源码，注释保留可读版本。

为什么不能为了给 fork PR 跑测试或拿 Secrets 而改用 pull_request_target？

pull_request_target 运行在基准仓库高权限上下文中，若 checkout 或执行 PR 代码，外部贡献者即可窃取 Secrets 或篡改仓库。fork PR 无法读取 Secrets 是正常且必要的安全边界。

默认生成的 workflow 会顺带配置自动发版或生产部署吗？

不会。默认只生成只读 CI；Release、推送镜像与生产部署必须先确认目标、GitHub Environment、OIDC 权限、required reviewers 与回滚方案，再拆分为独立 job 或独立 workflow。

如果本机没有安装 actionlint，技能会怎么验证生成的 workflow？

会明确标注 actionlint 未执行，绝不谎称通过；同时继续完成 YAML 解析、表达式注入排查、全量 uses: SHA 审计、persist-credentials: false 核对及本地测试命令复验。
