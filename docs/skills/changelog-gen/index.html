changelog-gen：基于真实 Git 历史的中文 CHANGELOG 生成器

发版前不用再把几百条 git log 复制粘贴给模型胡乱润色。changelog-gen 同时兼容标准 Conventional Commits 与非规范中文自由提交，自动合并 wip / fix typo 过程噪声、推导 Semantic Versioning 版本号，并严守「零编造编号、只读起草、绝不顺手打 tag」红线。

7b42e10 2026-11-24 feat(export): 支持批量 CSV 导出 (#134)

生成的中文 CHANGELOG 草稿 SemVer 建议：1.2.0 → 2.0.0 
## [2.0.0] - 2026-11-25

### ⚠️ Breaking Changes
- **移除废弃接口 `/api/v1/users`**，统一迁移至 `/api/v2/users` (#130)

### ✨ 新功能
- 支持批量 CSV 数据导出 (#134)

### 🐛 Bug 修复
- 修复分页查询偏移量边界错误

### 📝 文档更新
- 补充 Windows PowerShell 安装说明
🛡️ 防编造与噪声过滤审计结论
1）仅对提交中真实存在的 (#130)、(#134) 保留编号，4e91a03 未带 PR 号则直接省略不补编；2）自动折叠无用户价值的 `fix typo` 过程提交；3）检测到 `!` 破坏性标识，自动置顶 Breaking Changes 并建议主版本升至 2.0.0；4）仅输出草稿，未改动 CHANGELOG.md 且未执行 git tag。

🧭 4 步生成流程与 SemVer 版本号规则

1

确定真实提交范围与历史风格

先用 git describe --tags --abbrev=0 定位最近发布标签，再用 git -c core.quotepath=false log --no-merges --pretty=format:"%h %ad %s" --date=short <last-tag>..HEAD 跨平台读取真实提交；若已有 CHANGELOG.md，优先沿用其原有标题层级、日期格式与分类风格。

2

双模式分类提交（规范精准识别 / 非规范降级读 diff）

规范仓库按 feat、fix、fix(security)、perf、refactor、docs、deps 及 BREAKING CHANGE: / ! 精准归类；非规范中文自由提交则结合 git show --stat <sha> 与必要 diff，按面向用户可见影响人工归纳，不看标题猜内容。

3

推导 Semantic Versioning 版本号建议

存在 Breaking Changes 主版本 +1（1.2.0 → 2.0.0）；存在新增功能次版本 +1（1.2.0 → 1.3.0）；仅修复、安全补丁或维护修订版本 +1（1.2.0 → 1.2.1）；预发布版本支持 -alpha.1、-beta.1、-rc.1 后缀。

4

合并过程提交、预览确认后 UTF-8 追加

合并同一功能的琐碎提交（如“fix typo”“wip”），省略无实质改动的空分类小节；写入 CHANGELOG.md 前展示完整预览，经你确认后再以 UTF-8 编码追加至文件顶部。

8 类标准图标与归类依据

分类 Conventional 标识 / 归类依据 发版位置要求
⚠️ Breaking Changes 含 BREAKING CHANGE:、! 或破坏兼容的接口/配置变更 必须置于最前并加粗提醒，必要时附迁移指引
🔒 安全修复 fix(security) 或明确标注安全缺陷 / 真实 CVE 仅引用提交中真实存在的 CVE，绝不杜撰
✨ 新功能 / 🐛 Bug 修复 feat / fix 或面向用户的新增能力与缺陷修复 聚焦用户可见变化，合并琐碎过程提交
⚡ 性能优化 / ♻️ 重构体验 perf / 对用户或二次开发有感知的 refactor 无实测数据时严禁编造“提速 50%”类比例
📝 文档 / 📦 依赖与构建 docs、deps、chore(deps)、CI 与工程脚本 无实质变动时直接省略，不留空标题

🛡️ 发版安全与零编造红线

🚫 三条绝对不可触碰的红线
  • 绝不顺手打标签或发 Release：即使生成了完整发版说明，也绝不自动执行 git tag、推送标签或调用 GitHub Release API。
  • 零编造 PR / Issue / CVE 与性能数据：提交记录里没有编号就直接省略，禁止填写 (#xxx) 或瞎编 CVE；没有真实基准对比就不写具体性能百分比。
  • 脱敏内部敏感信息：生成的公开更新日志不得泄露内部敏感路径、测试凭据或私有内网域名。

❓ 常见问题 FAQ

仓库之前没打过任何 git tag，也能生成更新日志吗？

可以。当 git describe --tags --abbrev=0 查不到旧标签时，技能会改用明确的起止提交区间或全量提交历史进行归类，不会直接报错中断。

老项目里全是“修了个 bug”“更新接口”这种中文提交，它能分准吗？

能。遇到非规范提交会自动切入模式 B，通过 git show --stat <sha> 和必要的真实 diff 核实实际影响，再按面向用户可见改动归类，而不是只靠模糊标题瞎猜。

为什么严禁它顺手打 tag 或发布 GitHub Release？

打 tag 与发布 Release 往往会直接触发 CI/CD 发包或生产部署。将「起草更新日志」与「执行发版动作」彻底解耦，能防止误发版造成不可逆事故。

已有 CHANGELOG.md 用的是 Keep a Changelog 格式，会破坏原格式吗？

不会。第 1 步就会检查现有 CHANGELOG.md，沿用你原来的标题层级、日期格式和分类风格，并在确认后以 UTF-8 编码追加到文件顶部。
