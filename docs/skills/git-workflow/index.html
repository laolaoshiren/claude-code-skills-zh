🚦 交互式 Git 操作安全门禁选择器

点击下方 4 类日常 Git 场景，查看 git-workflow 对应的授权等级、必跑前置命令、边界约束与绝对红线：

只读审查：状态盘点与 Commit / PR 文案起草

默认只读 · 零写入副作用
1. 授权与适用边界

查看工作树、未跟踪文件、分支 upstream 关系、远程差异，以及起草 Conventional Commits 提交说明或 PR 描述，均不改动暂存区与提交历史。

2. 必做前置核验

先阅读仓库 AGENTS.md、CONTRIBUTING.md 与近期 git log 风格，同时检查未暂存与已暂存 diff，绝不只看 staged diff 下结论。

3. 绝对禁止红线

生成 commit message 不等于允许 git add / git commit；不得在只读分析阶段擅自清理未跟踪文件、修改分支或自动执行 stash。

git status --short --branch && git diff && git diff --cached && git log --oneline -10

🧭 5 步可验证 Git 工作流

每一步都以仓库真实状态和退出码为依据，优先使用非交互命令，拒绝凭记忆猜分支名或补跑假验证：

1

读取仓库规则与完整状态

先读 AGENTS.md、CONTRIBUTING.md 和 CI 说明，再执行 git status --short --branch、git diff、git diff --cached、git log --oneline -10、git remote -v 与 git branch -vv，完整掌握未跟踪文件和 upstream 偏移。

2

拆分授权并逐文件精确暂存

存在无关修改时严禁 git add . / git add -A；仅逐个 git add <file> 选中本轮改动，并用 git diff --cached 复核，避免把本地草稿或调试文件混入提交。

3

按真实 Diff 规划原子提交

根据实际改动判定 feat / fix / docs / refactor / test / perf / chore，沿用仓库近期提交语言和 scope；一个提交只表达一项可独立验证的变更，仅在确认应自动关闭时写入 Closes #123。

4

安全验证后提交并核验 HEAD

先确认测试/lint 脚本不会私自拉依赖或触发外部副作用，再运行相关验证并记录真实结果；commit 后执行 git status --short --branch 与 git show --stat --oneline HEAD 核验落盘状态；推送前必先 git fetch 检查远程新提交。

5

生成结构化、可复核的 PR 描述

仅在用户要求时创建 PR，文案固定包含「变更摘要、关键改动、验证结果、风险与回滚、关联 Issue」，只勾选真实跑过的检查项，最后用中文汇报已执行动作、commit SHA、推送/PR 链接及待定项。

⚖️ 动作权限拆分表与 Rebase / Force-Push 红线

Git 动作 默认权限与门禁 风险等级
状态检查、生成 commit message / PR 文案 只读，可直接执行，不改动仓库状态 只读安全
逐文件暂存（git add）、创建 commit 仅用户要求后执行，只选本轮文件并用 git diff --cached 复核 需明确要求
创建或切换分支 仅用户明确要求时执行；流程需要但未获授权时先说明原因征求同意 需明确要求
fetch、push、创建 PR 分别确认在请求范围内，互不推导；push 前必须先 git fetch 逐项授权
merge PR、关闭 Issue、发布 Release 高影响外部状态变更，必须获得明确指令 严格授权
rebase、改写已发布历史、强推远程 高风险；绝不对公共分支 rebase，禁止 --force，遇冲突立即停止上报 高危红线

工作树与历史保护机制

  • 把已有未提交改动、未跟踪文件和无关修改视为用户资产，不覆盖、不回退；
  • rebase 前要求工作树与暂存区完全干净，必要时在用户允许下先建本地备份引用；
  • 发生合并/变基冲突时立即停止，列出冲突文件与可选方案，不擅自猜测业务归属。

明确禁止的越权行为

  • 严禁 git push --force；私有分支经授权重写后，仅允许先确认远程状态再用 --force-with-lease；
  • 严禁未经授权自动 git stash、git reset --hard 或丢弃用户本地修改；
  • 严禁把未运行或基线原本失败的检查项在 PR 描述里勾选为「已通过」。

❓ 常见问题 FAQ

为什么 git-workflow 禁止顺手执行 git add . 或 git add -A？

日常开发中工作树里常常留有草稿、调试代码或另一项任务的未提交文件。存在无关改动时执行 git add . 会把无关资产混进提交历史；git-workflow 要求逐个暂存本轮文件，并在提交前用 git diff --cached 二次核验。

让它生成 commit message 或创建提交，会自动 git push 或发 PR 吗？

不会。分析状态、暂存提交、切换分支、推送远程、发起 PR 与合并 PR 均按独立授权处理，互不自动推导，确保远端分支状态完全在你的掌控之内。

什么情况下允许 rebase，对 force push 的红线是什么？

仅在用户明确授权、工作树与暂存区干净且目标不是公共分支或他人依赖提交时才可执行 rebase；任何情况下禁止 git push --force，已授权重写的私有分支也只能在重新确认远程状态后使用 --force-with-lease。

提交前如何做测试验证？如果项目基线原本就有失败怎么办？

运行验证前会先确认脚本不会私自下载依赖或调用外部服务，再跑与改动相关的测试/lint/构建并附真实退出状态；基线已有失败会如实单列，绝不伪造通过。
