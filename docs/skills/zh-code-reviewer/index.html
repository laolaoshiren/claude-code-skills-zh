🧭 5 步高信号审查流程（先追踪调用链，再做误报三连问）

1

确定审查范围与仓库基准

使用 git -c core.quotepath=false status --short 与 diff --stat 读取真实变更（防 Windows 中文路径转义），并先读项目既有 AGENTS.md、tsconfig 与 lint 规则，不拿个人喜好覆盖团队规范。

2

追踪上下游调用链与契约

读取变更所在的完整函数/类上下文，核查公开 API、Schema、CLI 行为和错误处理路径，识别隐式破坏性变更（breaking change）。

3

五大高信号维度逐项排查

聚焦：正确性与边界条件（含 UTF-8/GBK 与跨平台假设）、并发与资源泄漏、安全与越权注入、热路径性能退化（N+1 / 无界内存）、契约兼容与测试覆盖。

4

误报自检三连问

落笔前强制自检：① 真实运行路径是否可达？② 上游中间件或框架是否已拦截？③ 修复方案是否可执行且无新副作用？过滤掉可由 linter 自动处理的纯格式问题。

5

分级输出 + 诚实披露未跑验证

输出含「总体结论 / 三级发现 / 测试覆盖检查 / 待确认问题」的标准中文报告；未实际跑测试时绝不宣称“测试通过”，发现敏感凭据仅报告行号并严格脱敏。

❓ 常见问题 FAQ

审查完如果没有问题，它会强行挑刺凑字数吗？

不会。规则要求若范围内未发现阻塞或重要缺陷，必须明确写「在本次审查范围内未发现阻塞合并的缺陷」，并列出覆盖范围与未跑验证项。

发现代码里误提交了真实 Token 或密码会直接打印出来吗？

不会。安全边界严禁回显真实凭据全文，仅报告所在文件与行号并提示脱敏轮换。
