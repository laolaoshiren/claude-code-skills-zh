⚡ 批量核验防限流：单次 GraphQL 批量取数

✅ 推荐做法：批量 GraphQL 一次查清

  • 单个候选仓可用 gh repo view 与只读 contents 接口核验元数据与根目录资产；
  • 批量核验多个候选仓时，优先合并为单次 gh api graphql 批量获取 Star、归档状态、许可证与根目录结构，避免逐仓轮询触发限流或账号风控；
  • gh 不可用时改用公开网页只读核验，并在「核验说明」中如实标注未确认项，严禁猜测 Star。

🚫 硬性淘汰 vs 必须显式提示

  • 直接淘汰：404/私有/空仓/已归档无替代、与 Agent 生态无关、看不到实际资产、涉及盗号/恶意攻击/绕过付费/违法采集/明显侵权、名实不符；
  • 显式提示（按风险扣 0–30 分）：强依赖商业 API 或云端浏览器、会自动发帖/操作交易、涉及爬虫/Cookie/账号风控、许可证受限或长期失修；
  • “官方”“生产级”“最大”“首个”等定性词必须有可核验证据。

❓ 常见问题 FAQ

一个高星仓库（比如几千 Star）可以直接跳过资产核验直接收录吗？

绝对不行。skill-curator 明确规定「不要因 Star 低而自动拒绝，也不要因 Star 高而跳过资产核验」。很多高星仓库只有营销落地页、概念文案或商业引流说明，必须确认真实存在 SKILL.md、plugin.json、agents/、MCP Server、CLI 或明确可复现的安装命令。

为什么批量核验候选仓时强调合并为一次 gh api graphql 查询？

逐仓库、逐文件高频调用 REST API 很容易触发 GitHub 限流甚至账号风控。skill-curator 优先将多个候选仓库的元数据与根目录结构合并进单次 gh api graphql 只读请求，既高效又合规。

只是让 skill-curator 评估候选链接，它会自动改 README 或合并 PR 吗？

不会。用户只要求评估时，skill-curator 仅输出结构化核验报告、评分、推荐分类与规范中文文案，不修改仓库或 GitHub 状态；仅当用户明确要求加入精选列表且候选通过核验后，才先更新 README 再运行官网同步与项目检查。

涉及自动发帖、浏览器自动化或强商业 API 依赖的仓库会被直接淘汰吗？

不一定直接淘汰（除非涉及盗号、恶意攻击、绕过付费、违法采集或明显侵权），但会按风险扣 0–30 分，并在核验报告与收录文案中显式写明前置条件、账号风控、订阅依赖或许可证限制，严禁暗示无风险全自动运行。
