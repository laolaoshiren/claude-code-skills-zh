门禁 1：只读扫描硬编码 UI 文本并精准排噪

阶段 1 / 4 · 只读盘点
核心动作

先读 package.json / pyproject.toml / go.mod / pom.xml 识别已有 i18n 设施与命名风格，再扫描目标目录中的前端或后端源文件，汇总面向用户的 UI 文本、表单校验与错误提示。

重点排噪与拦截项

自动排除日志调试信息、SQL、正则、URL、import 路径、代码注释、内部枚举与默认测试断言；每条候选均标注所在上下文（组件 / 纯函数 / 模板）。

门禁放行条件

输出完整「文件:行号 · 原文 · 建议 key · 上下文类型」清单，等待用户明确确认本次改造范围；未获确认绝不修改任何业务源码。

🗂️ 支持的多语言框架、文件格式与对账能力

先匹配项目既有语言包结构（扁平点分或嵌套对象），再做基准语言与目标语言的完整性对账：

语言包格式 常见技术栈 / 框架 技能核查重点
JSON (.json) i18next / react-i18next / react-intl / next-intl 保持扁平或嵌套风格一致，校验 JSON 合法性、缺失 key、孤儿 key 与 {name} / {{count}} 占位符一致
YAML (.yaml / .yml) vue-i18n 等前后端配置 显式 UTF-8 无 BOM 写入，区分 <template> 内 $t()、<script setup> 内 useI18n() 与纯 TS 调用
PO / POT (.po) Python / C / Go 等 gettext 工作流 完整保留 msgid / msgstr 结构、上下文标记与复数规则，校验 %s 格式占位符
Properties (.properties) Java Spring MessageSource 先核对项目规范要求 UTF-8 直写还是 \uXXXX 转义，再统一写入，避免混用导致乱码

⚖️ 触发边界与国际化编码红线

高可靠实践准则

  • 适用：业务代码硬编码 UI 文案提取、多语言库接入、语言包缺失 key 与占位符对账；
  • 保留专有技术术语（API、SDK、HTTP、OAuth 等）与品牌名，不做机械直译；
  • 日期、数字与货币优先采用 Intl.DateTimeFormat / Intl.NumberFormat 等 locale 感知 API；
  • 改造后如实运行 tsc --noEmit、lint、构建或相关测试，未执行时明确标注「已修改、未执行构建验证」。

明确禁止的越界与翻车写法

  • 不适用：汉化第三方英文 SKILL.md / AGENTS.md / CLAUDE.md → 请使用 skill-translator；
  • 严禁在普通工具函数、常量定义、类方法或模块顶层调用 useTranslation() 等 React Hook；
  • 严禁把文案和变量用 + 字符串拼接翻译，必须改为命名插值（如 t('welcome', { name })）或保留 <Trans>；
  • 严禁未经用户授权执行 npm install / pip install、改写 lockfile 或覆盖工作树已有改动。

❓ 常见问题 FAQ

i18n-helper 和 skill-translator 有什么区别，什么时候该用哪个？

i18n-helper 面向前端/后端业务源码的多语言接入与缺失 key 巡检；如果你的目标是把英文 SKILL.md、AGENTS.md 或 CLAUDE.md 本地化为地道中文，请使用 skill-translator。

在 React 项目批量替换文案时为什么容易引发 Hooks 报错？i18n-helper 怎么防？

在普通函数、常量表或模块顶层调用 useTranslation() 会直接违反 React Hooks 规则并导致运行时崩溃。技能在扫描清单阶段即标注上下文类型，非组件场景强制改为传入 t、使用 i18n.t() 或返回 key 由组件层渲染翻译。

扫描完会直接把整个仓库的业务代码都改写吗？项目未装 i18n 依赖怎么办？

不会。默认先输出待确认清单并核对 git status；如果仓库尚未安装 i18n 依赖，会先给出选型与安装方案，未经明确授权绝不执行包安装或批量改码。

Windows 环境下生成中文语言包为什么容易乱码，技能如何处理？

Windows 默认代码页常为 CP936/GBK，直接落盘极易破坏 JSON/YAML/PO 中的中文字符。i18n-helper 强制全部语言文件以 UTF-8（无 BOM）读写，并在改造后用构建和 git diff 双重核验。
