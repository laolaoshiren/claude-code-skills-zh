🚨 上手前必看的三条硬坑与边界

1. 插件标识符已简化为 ecc@ecc，且严禁与 --profile full 混用

早期文章常出现较长标识符，现已统一为 /plugin install ecc@ecc。如同时运行 --profile full，会导致技能与 Hooks 重复注册、Token 暴涨甚至死循环。

2. /multi-* 多智能体编排命令必须单装 ccg-workflow

想运行 /multi-plan、/multi-execute、/multi-backend、/multi-frontend 或 /multi-workflow，需额外执行 npx ccg-workflow 安装 ~/.claude/bin/codeagent-wrapper 与对应 prompts，否则无法执行。

3. 复制 rules 时必须拷贝整个语言目录 & 分离记忆进程

不要只拷贝 rules/ 里的单个 .md，必须整目录拷贝（如 rules/common、rules/golang）以保证相对引用正常；多工具接入 ecc-memory-vault 时，不同 harness 需通过 ECC_MEMORY_HARNESS 各自启动独立 MCP 进程。

❓ 常见问题 FAQ

Q1：国内开发者第一次看 ECC 仓库文件那么多，从哪几份文档读起？

建议按原仓顺序：先看 README.zh-CN.md 快速开始，再按需查阅根目录下 the-shortform-guide.md（速览）、the-longform-guide.md（深度工作流）和 the-security-guide.md（安全边界），不要一次性把 328 个技能全塞进上下文。

Q2：以前用过 /tdd、/eval、/verify 等老命令，现在找不到怎么办？

原仓已在 legacy-command-shims/ 中归档了退役短命令并给出迁移指引：例如用 tdd-workflow 技能替代 /tdd，用 verification-loop 替代 /verify，用 eval-harness 替代 /eval。

Q3：ECC 跟 obra/superpowers 有什么定位差异？可以同时用吗？

affaan-m/ECC 偏「全栈工具箱 + 规则库 + 语言审查命令 + 持续学习本能」；obra/superpowers 偏「强制先出规格、再走红绿 TDD 与子代理两阶段审校的研发流程」。两者可互补，但建议不要在同一项目里同时开启两套冲突的 TDD/plan 触发规则，先选一套作为主流程。

Q4：只想给现有英文 Skill 做汉化或先做单点 Code Review，需要装整个 ECC 吗？

不需要。轻量场景可直接安装本仓库自带的 zh-code-reviewer、security-audit 或 skill-translator 单个 MIT 技能；当你希望给整个团队沉淀跨语言的规则、Hooks 与记忆体系时再引入 ECC。
