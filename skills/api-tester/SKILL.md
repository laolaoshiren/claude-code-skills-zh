# API 测试助手

## 触发边界

**适用场景：**

- 为 HTTP / REST / GraphQL / gRPC 路由、Controller 或 Handler 编写或补齐接口测试与契约验证。
- 校验 OpenAPI / Swagger 规范与真实路由实现之间的一致性（发现 Spec Drift）。
- 复现接口缺陷、验证接口向后兼容性或补齐认证/鉴权/参数校验回归用例。

**不适用场景：**

- 纯函数、工具类、领域模型或模块内部逻辑的单元测试与非接口层集成测试 → 请使用 `test-generator`。
- 接口压测、吞吐量基准或慢接口火焰图定位 → 请使用 `perf-profiler`。
- 专项安全渗透探测、模糊测试或漏洞扫描 → 请使用 `security-audit`。
- 纯前端页面交互 E2E 测试或从零撰写公开接口文档 → 请使用对应前端测试流程或 `zh-docgen`。

## 核心原则

- 只把可核验的 OpenAPI、路由代码、验证器、统一响应拦截器、类型定义、调用方或现有测试当作契约证据。
- 生成测试不等于执行测试；读取接口定义不等于可以访问真实服务。
- 严格遵守凭据零明文原则，保护现有数据、凭据和用户修改，优先使用隔离且可清理的测试环境。

## 工作流程

### 1. 读取项目与接口证据

先读取适用的仓库规则、测试说明、Git 状态和项目脚本，再按以下优先级提取契约证据：

1. **规范层**：OpenAPI / Swagger / GraphQL Schema / `.proto` 文件及其引用的 Schema。
2. **无 OpenAPI 时的标准降级取证链**（当项目缺少接口文档或使用动态语言/无强类型 DTO 时）：
   - 路由注册表、鉴权/限流/参数校验中间件与 DTO/Validator；
   - Controller / Handler 的入参解构、状态分支与返回语句；
   - **全局响应拦截器与业务错误码枚举**（特别注意国内项目高频使用的 **HTTP 200 + 统一业务信封** 如 `{ code, msg, data }` 模式，避免只盯 HTTP 状态码而遗漏业务错误码契约）；
   - 现有前端/SDK 调用方、现有接口测试及数据库模型约束。
3. **测试基础设施**：测试配置、fixture、认证方式、环境变量模板和数据清理机制。

记录规范、实现与现有测试之间的不一致，不做静默取舍。

### 2. 建立契约矩阵与缺省/冲突三级处置

为每个目标 endpoint 记录：

| 项目 | 证据来源 |
|------|----------|
| method 与 path | OpenAPI 或路由注册位置（文件:行号） |
| 认证与权限 | security scheme、鉴权中间件或调用方 |
| 请求参数与约束 | Schema、DTO、验证器或入参解析代码 |
| 已声明响应与业务信封 | HTTP 状态码、统一信封（如 `code`/`msg`/`data`）与 header |
| 副作用与幂等性 | 实现代码、数据库/外部调用链或文档 |
| 测试环境与清理 | fixture、内存库、事务回滚或 teardown |

不要默认每个接口都应返回 `400`、`401`、`403`、`404`、`422` 或 `500`。只有契约已声明或代码路径真实可达时才生成对应断言。遇到契约缺失或冲突时，按三级策略处置：

- **规范与实现一致**：生成正式的精确状态码、业务码与响应结构断言。
- **缺少 OpenAPI 但代码路径明确可达**：生成现状回归测试，并在报告中标明「依据代码实现 `file:line` 反推，待业务确认」。
- **OpenAPI 与代码实现冲突（Spec Drift）**：严禁擅自修改业务代码或文档去迁就测试；对争议断言标为 `skip`/`todo`（附注释说明偏差），并在输出报告的「契约偏差与风险发现」中单列暴露，交由用户决策。

### 3. 三档环境与授权门禁

执行任何测试或请求前，先判定执行环境所处档位，避免一刀切阻断离线测试或漏判本地进程的远程副作用：

| 档位 | 环境特征 | 授权与前置核查要求 |
|------|----------|--------------------|
| **档位 1：纯进程内离线测试** | `supertest(app)`、FastAPI `TestClient`、`httptest.NewRecorder()`、Spring `MockMvc` 等，搭配 Mock 或内存/临时隔离库 | 核实测试不会外连真实数据库、消息队列或外部 API 后，可直接运行仓库已有测试命令，无需机械追问 Base URL 与测试账号 |
| **档位 2：本地服务进程** | 访问 `localhost` / `127.0.0.1` 或本地容器服务 | **不能仅凭 localhost 判定安全**：必须先检查环境变量模板/配置，确认 `DATABASE_URL`、`REDIS_URL` 及支付、短信、邮件、OSS 等三方 SDK 均指向隔离测试实例且具备清理方案 |
| **档位 3：远程或第三方环境** | 共享 dev、staging、production、付费 API 或外部服务 | 必须逐项获得用户明确授权：目标 Base URL、环境归属、测试账号与权限范围、是否允许写操作（POST/PUT/PATCH/DELETE/上传/通知等）、配额/计费影响及数据清理方案 |

用户只要求“生成测试”时只产出代码。GET 也不能仅凭 method 判定无副作用（如可能触发审计写入、令牌消费或状态变更）。

### 4. 选择项目锁定的工具

- 优先运行仓库已有的 test、OpenAPI lint 或 contract test script。
- 读取 package manager、lockfile 和已安装版本后再选择命令。
- 不用裸 `npx`、全局工具或临时下载的最新版解析规范。
- 缺少依赖时先报告；安装工具、更新 lockfile 或修改测试配置需要单独授权。
- 使用真正的 YAML / JSON / OpenAPI 解析器，不用 `grep` 推断嵌套 Schema。

### 5. 设计有依据的用例

按目标契约选择必要场景：

- 成功路径：使用最小合法输入验证 HTTP 状态、业务信封结构与关键语义。
- 边界路径：只测试 Schema 或实现中真实存在的长度、范围、枚举、格式和必填约束。
- 认证与权限：只覆盖已声明的身份、角色和资源归属规则。
- 失败与回归：覆盖可达错误路径、已知缺陷或兼容性要求。
- 幂等、分页、并发、重试与超时：仅在接口契约包含这些语义时测试。

断言外部可观察行为，避免绑定内部函数调用。随机数据应固定 seed，并避免真实个人信息、客户数据和生产标识。

### 6. 实现最小测试

- 沿用项目现有框架、目录、fixture、命名和断言风格。
- 单元测试可隔离网络、时间和第三方服务；集成测试使用受控服务或临时资源。
- 对写操作使用唯一测试标识，并在成功、失败和中断路径都执行清理。
- 不为让测试通过而擅自修改生产代码、接口规范或认证配置。
- 使用跨平台路径 API 与显式 UTF-8 编码；若提供手工复现命令，注意 **Windows PowerShell 中 `curl` 是 `Invoke-WebRequest` 别名**，应使用 `curl.exe` 或项目测试运行器，并避免单引号 JSON 转义问题。

### 7. 执行与复验

1. 先检查命令是否会下载依赖、访问外部服务或改变共享状态。
2. 运行最小目标测试，记录命令、环境档位、退出状态和真实响应摘要。
3. 按风险运行相关测试、类型检查或完整测试。
4. 检查 Git diff 和环境状态，确认没有残留测试数据、快照、日志、凭据或无关生成物。
5. 将基线已有失败与本轮新增失败分开报告。

没有实际运行时，只能说明“已生成、未验证”。没有明确 SLA 和受控测量条件时，不添加固定耗时断言或声称性能达标。

## 安全边界

- **凭据零明文**：仅通过环境变量名引用凭据（如 `process.env.API_TOKEN`、`os.environ["API_TOKEN"]`），严禁读取 `.env`、`~/.netrc` 或 Cookie 明文并展开拼入命令行、测试源码、fixture、日志或报告中。
- 未经明确授权，不访问生产环境、真实客户账号、付费 API 或受监管系统。
- 压测、模糊测试、大批量数据生成和安全探测需要单独授权及限流方案。
- 遇到权限不足、环境档位不明、本地进程直连远程共享库、清理方案缺失或响应可能含敏感信息时，停止执行并报告。

```markdown
> 执行状态统一使用：`已运行通过` / `已运行失败（产品缺陷或契约冲突）` / `仅生成未执行（缺环境或未授权）` / `跳过（待确认）`

```
